我把 Nanobot 的思路拆成两层实现。第一层是 Runtime 层，对应 com.wenhui.agent，负责 Agent Loop、工具路由、上下文管理和验证闭环；第二层是业务 Agent 层，对应 reference-service，负责企业知识库客服里的意图识别、知识检索和答案生成。这样既保留了 Nanobot 轻量 Runtime 的思想，又能落到 Java/Spring Boot 的业务系统里。

我先用规则策略验证 Agent Runtime 的状态流转和工具闭环，再把策略层抽象成 AgentPolicy，后续通过 LlmAgentPolicy 接入大模型，让模型根据工具描述和历史 Observation 自主完成 ReAct 决策。这样 Runtime 不依赖具体模型，工具系统和模型推理可以解耦演进。

我把 RAG 链路拆成离线入库和在线召回两部分。离线侧先将企业知识文档切分成 Chunk，再做 Embedding 向量化，并写入 Milvus 向量集合；在线侧对用户问题做同样的向量化，通过 TopK 语义召回拿到最相关知识片段，再交给答案生成 Agent。这样系统回答不是直接依赖模型自由生成，而是基于有来源、有置信度的知识证据生成。

我没有把 Milvus 写死在检索 Agent 里，而是抽象了 VectorStore。开发验证时走 LocalVectorStore，生产环境通过配置切到 MilvusSdkVectorStore。入库时文档先切 Chunk，再做 Embedding，并 upsert 到 Milvus collection；查询时用户问题向量化后通过 Milvus TopK 召回，再交给答案生成 Agent。

我把多轮上下文抽象成 ConversationMemoryStore，默认本地验证，生产环境切 Redis；把文档元数据、问答日志和用户反馈抽象成 KnowledgeAuditRepository，MySQL 侧通过 MyBatis-Plus Entity、Mapper 和 Repository 适配。这样客服系统不仅能回答问题，还能追踪每轮问答、保存反馈并支撑后续效果分析。

“我没有把 Prompt Engineering 只理解成写一段提示词，而是拆成模板构建和策略执行两层。模板层把 system 角色约束、会话摘要、用户问题、解析后的追问和 RAG 召回证据拼成 grounded prompt；策略层会先判断证据是否存在、来源是否完整、置信度是否达标，再决定 evidence-only 回答还是转人工处理。最终 prompt 版本和策略结果会进入 trace 和 QA 日志，方便后续排查模型幻觉和做效果分析。”
