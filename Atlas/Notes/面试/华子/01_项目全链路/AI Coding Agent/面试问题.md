1. 你现在真的接了 Embedding 模型吗？

答：  
当前工程里还没有接真实 Embedding 模型，先用了 HashingEmbeddingModel 做本地向量化，目的是验证 RAG 主链路，包括文档切分、向量入库、TopK 召回和低置信度兜底。真实落地时会把 EmbeddingModel 接口替换成 HTTP Embedding 服务，比如 BGE、M3E、通义千问 Embedding 或 OpenAI-compatible embedding API。

2. 为什么先用 HashingEmbeddingModel，而不是直接接真实模型？

答：  
因为我想先把系统边界和链路跑通。Embedding 是可替换的基础能力，真正复杂的是链路设计：文档如何切分、向量如何入库、检索结果如何带回 Agent、低置信度如何兜底。现在 EmbeddingModel 已经抽象成接口，替换真实模型不会影响 RagPipeline 和 KnowledgeRetrievalAgent。

3. Milvus 现在是真的接了吗？

答：  
接入层已经写了真实 Milvus SDK 版本，也就是 MilvusSdkVectorStore。它负责连接 Milvus、创建 collection、upsert 向量和 TopK search。默认配置走 LocalVectorStore，是为了不启动 Milvus 时也能本地验证。启动 Milvus 后通过 RAG_VECTOR_STORE=milvus 就能切到真实 Milvus。

4. 为什么要同时保留 LocalVectorStore 和 MilvusSdkVectorStore？

答：  
这是为了区分开发验证和生产环境。开发阶段不依赖外部服务，可以用本地向量库快速跑通链路；生产环境切到 Milvus。两者都实现同一个 VectorStore 接口，所以业务 Agent 不关心底层存储，降低耦合。

5. 你的 RAG 链路怎么走？

答：  
分两段。离线入库时，企业文档先经过 DocumentChunker 切成 Chunk，再通过 EmbeddingModel 向量化，最后写入 VectorStore，生产环境就是 Milvus。在线查询时，用户问题也走同一个 Embedding 模型向量化，然后在 Milvus 里做 TopK 相似召回，把召回的知识片段交给答案生成 Agent。

6. 为什么要做文档切分？

答：  
因为企业文档通常比较长，直接整篇向量化会导致语义粒度太粗，也容易超出模型上下文窗口。切分成 Chunk 后，每个片段表达一个相对集中的语义单元，召回更精确，答案生成时引用的依据也更清楚。

7. Chunk 大小怎么定？

答：  
当前代码里先按词数做了固定窗口切分，并保留 overlap。真实项目中会根据文档类型调整，比如制度类文档可以按标题和段落切，FAQ 可以按问答对切，接口文档可以按模块切。Chunk 太大会降低召回精度，太小会丢上下文，所以一般会结合召回效果评估调整。

8. 为什么需要 overlap？

答：  
因为边界附近的信息可能被切断。Overlap 可以让相邻 Chunk 保留一部分上下文，减少“答案依据刚好跨两个 Chunk 导致召回不完整”的问题。

9. TopK 怎么选？

答：  
当前默认取 Top3。TopK 太小可能漏召回，太大又会引入噪声，影响答案生成。真实项目中会根据命中率、人工评估、答案准确率来调参，也可以结合 score threshold 做过滤。

10. 你怎么判断召回结果是否可信？

答：  
召回结果里有 score。答案生成 Agent 会看最高置信度，如果低于阈值，就不直接生成答案，而是走低置信度兜底，比如提示转人工或补充信息。这样可以降低幻觉。

11. RAG 怎么降低幻觉？

答：  
主要靠两点：第一，答案生成只基于召回片段，不让模型自由发挥；第二，低置信度时不生成确定性答案，而是转人工或提示信息不足。后续接 LLM 时还会在 Prompt 里明确要求“只能依据检索内容回答，缺少依据时说明无法确认”。

12. Milvus collection 里存了哪些字段？

答：  
核心字段包括 chunk_id、document_id、title、intent_name、content 和 embedding。embedding 用于向量检索，其他字段用于过滤、回显来源和答案引用。

13. 为什么 collection 里要存 intent_name？

答：  
因为客服问题通常有业务意图，比如售后、知识问答、工单咨询。检索时可以先按 intent 过滤，再做向量相似度召回，能减少跨业务误召回。

14. 为什么用 Milvus，不用 MySQL 存向量？

答：  
MySQL 更适合结构化数据和事务管理，不适合大规模向量相似度检索。Milvus 专门为向量检索设计，支持高维向量索引、TopK 相似搜索和大规模数据召回。MySQL 可以存文档元数据和日志，Milvus 负责向量召回，两者职责不同。

15. 如果 Milvus 挂了怎么办？

答：  
可以做降级策略。比如短期返回“知识库检索服务不可用，请转人工”，或者切到缓存/关键词检索。代码层面因为有 VectorStore 接口，可以扩展 fallback 实现，不影响上层 Agent。

16. 文档更新后怎么处理向量库？

答：  
文档更新后重新切分并重新生成 Embedding。通过 chunk_id 或 document_id 做 upsert 或删除旧 Chunk，再写入新 Chunk。当前代码里 upsert 已经体现了这个思路。

17. 你怎么评估 RAG 效果？

答：  
可以从召回和回答两层评估。召回层看 TopK 命中率、MRR、召回准确率；回答层看答案正确率、引用依据是否匹配、低置信度兜底是否合理。业务上还可以结合用户反馈、人工审核和工单转化率。

18. 如果召回到了错误文档怎么办？

答：  
可以从几方面优化：调整 Chunk 策略，换更好的 Embedding 模型，加关键词和向量混合检索，加业务意图过滤，加 rerank 模型，或者提高 score threshold。当前代码先做了 intent 过滤和 score threshold 的基础设计。

19. 后续接真实 Embedding 模型怎么改？

答：  
新增一个 HttpEmbeddingModel 实现 EmbeddingModel 接口。它通过 HTTP 调用模型服务，把文本转成向量。然后在 RagKnowledgeRepository 里把 HashingEmbeddingModel 替换成 HttpEmbeddingModel，其他 RAG 和 Agent 代码不用改。

20. 你这个项目和 Nanobot 的关系是什么？

答：  
Nanobot 给我的启发是 Agent Runtime 的设计思想，比如 Agent Loop、工具路由、上下文和结果回填。我没有直接复制 Nanobot，而是把它的 Runtime 思想迁移到 Java/Spring Boot 技术栈，并落到企业知识库客服这个业务场景里。RAG 检索属于业务 Agent 的能力，Runtime 层负责调度和闭环。
