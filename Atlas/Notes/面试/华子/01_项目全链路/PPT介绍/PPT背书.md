**第二页讲稿**

这一页我想先从 Agent Runtime 的执行闭环讲起。这里展示的是我参考 Nanobot / OpenClaw 思想整理出来的一套 Agent Runtime 流程图，它不是单纯的一次模型调用，而是一个可持续执行、可观察、可回填上下文的循环系统。

最上面是用户输入。用户输入进入之后，首先会到 loop.py，也就是状态机入口。它负责整个任务的生命周期调度，包括接收输入、维护上下文、判断当前任务是否需要继续执行，以及控制什么时候进入下一轮循环。所以我理解 Agent Runtime 的第一层能力，就是**状态管理和流程控制**。

接下来进入 runner.py，也就是 ReAct 执行引擎。ReAct 的核心是让模型不是直接给最终答案，而是在推理过程中判断：当前需要不需要调用工具，如果需要，应该调用哪个工具，工具返回的 Observation 又应该如何进入下一轮推理。这个过程更接近“推理、行动、观察、再推理”的闭环。

再往下是 Registry，也就是能力路由网关。它的作用是把不同能力统一注册和调度起来，比如本地 Tool、内置 Skill、远程 MCP。在 Nanobot 的实现里，这三类能力进入系统的方式不一样。本地 Tool 会直接注册到 ToolRegistry，RUN 阶段由 Runner 根据模型返回的 tool call 执行，比如读取 runner.py 文件内容；内置 Skill 不是函数调用，而是在 BUILD 阶段读取 SKILL.md 并注入 system prompt，比如日志解析 Skill 会影响模型后续分析步骤；远程 MCP 则是在启动或请求前连接外部 MCP Server，通过 list_tools 获取工具 schema，再包装成 mcp_<server>_<tool> 注册进 Registry，比如 Playwright MCP 工具。这样 Agent 不需要知道每个工具的具体实现细节，只需要根据任务需要选择合适的能力。这个设计让我感觉很重要，因为 AI 应用真正落地时，模型本身只是决策节点，背后还要接很多业务工具、知识库、数据库和外部服务。

最下面是结果回填。工具执行之后，结果不会直接结束，而是会作为 Observation 回填到上下文里，再交给状态机判断是否进入下一轮。也就是说，Agent Runtime 的关键不是“调用一次模型”，而是形成一个可控的执行闭环：输入、状态调度、推理决策、工具调用、结果观察、上下文更新，再到下一轮决策。

这里我还想补充一个我比较关注的点，就是上下文压缩和记忆。像 Nanobot / OpenClaw 这类 Agent Runtime，在长任务场景下不会把所有历史内容都原样塞进上下文，而是会把旧上下文进行压缩，同时保留关键记忆和最近上下文。这样既能控制 token 成本，也能避免长任务执行到中间丢失目标。这个思想后面我迁移到了我的智能客服项目里，用 Redis 保存多轮会话摘要、当前意图和会话状态，支撑用户连续追问。

所以这一页对应到我的项目里，主要是一个设计思想来源：我参考 Agent Runtime 的可控执行闭环，把它落到 Java 企业知识库智能客服系统中。后面我的实现就围绕三个问题展开：第一，如何用状态机管理多 Agent 协同；第二，如何用 RAG 让回答有知识依据；第三，如何用记忆、Prompt 约束和日志反馈，让系统变得可追踪、可迭代。
